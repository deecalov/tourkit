# TourKit: GitHub and release checklist

## Repository layout

This repository contains the standalone TourKit package at its root. Run all
commands here. Node.js 22.13 or newer is required for development tooling;
`.nvmrc` selects Node.js 22. The published library retains its own runtime
compatibility declaration in `package.json`.

The repository was prepared from a source snapshot with a new Git history.
Local dependencies, builds, test reports, editor settings, internal integration
feedback and the reference Intro.js checkout are excluded. The public benchmark
uses the pinned npm development dependencies; no reference checkout is needed.

## Build and distribution outputs

| Command / destination    | Result                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `npm run build`          | `dist/`: ESM, CJS, browser-global bundles, TypeScript declarations and CSS                                            |
| `npm run prepublishOnly` | Lint, typecheck, unit tests, build, size budgets, package/type checks and packed-consumer smoke tests                 |
| `npm pack`               | An installable npm `.tgz` containing the distribution and package documentation                                       |
| GitHub Releases          | Versioned downloadable archives; source archives are generated by GitHub, compiled assets must be attached explicitly |
| `npm run site:build`     | `site/`: landing page, demo and guide/API documentation for Pages                                                     |

Use npm as the installation channel for bundler users. A release archive also
serves consumers who copy global builds and CSS into a server-rendered site.
Pages hosts the website and documentation; it is a separate deployment.

Keep release archives outside the source checkout. Run a build and its
consumer checks sequentially: rebuilding `dist/` while browser or package
tests read it can temporarily remove files.

## Validate before publishing

```bash
npm ci
npm run lint
npm run format:check
npm run typecheck
npm run test:coverage
npm run build
npm run size
npm run lint:pkg
npm run test:pack
npm run site:build
npx playwright install chromium firefox webkit
npm run test:e2e
```

Use `--with-deps` when installing browsers on Linux. Existing visual baselines
were captured on Windows. The CI workflow runs functional tests on Linux and
enables visual tests once Linux snapshots are present. Run the manual
**Update visual baselines (linux)** workflow to generate and review those images.
Its commit step requires Actions to have write access to repository contents;
branch protection may require applying the uploaded artifact through a PR.

## Upload to GitHub

Create an empty repository without a generated README or license. Commit this
folder and add the chosen remote:

```bash
git add .
git commit -m "Initial TourKit source release"
git remote add origin https://github.com/deecalov/tourkit.git
git push -u origin main
```

The remote above is the project identity already used in package metadata,
badges and links. If a different owner or repository name is chosen, update
those links, `package.json`, the docs navigation and the VitePress `base`
before publishing. No existing remote repository is changed by preparing
this folder.

## GitHub Pages

Enable **Settings > Pages > Source > GitHub Actions**, then run **Deploy site
(GitHub Pages)** from the Actions tab. Deployment is manual so uploading source
to a new repository does not attempt to publish an unconfigured Pages site.
The workflow builds the library, landing, demo and documentation into `site/`
and deploys that artifact. The default URLs are `/tourkit/`, `/tourkit/demo/` and
`/tourkit/docs/` on the owner's GitHub Pages host. VitePress uses
`/tourkit/docs/` as its base path.

## npm releases

The existing release workflow publishes on a pushed `v*` tag. It verifies that the tag
matches `package.json`, runs the package checks via `prepublishOnly`, publishes
to npm with provenance, and creates a GitHub Release using the matching
CHANGELOG section. Uploading the main branch does not publish an npm package.

### First publication

The npm distribution is named `sitetourkit`; the library and GitHub repository
retain the TourKit name. npm rejected the original `tourkit` name because it
was too similar to the existing `tour-kit` package. The unsuccessful `v0.7.0`
tag is retained; the first publication under the new name uses `v0.7.1`.

1. Select the maintainer's npm account and enable its two-factor authentication.
2. Recheck `npm view sitetourkit` immediately before releasing. A 404 means that the
   lookup did not find a published package; it does not reserve the name or
   prove that a publish will be accepted.
3. For the existing noninteractive bootstrap workflow, create an authorized
   granular package-write token with **Bypass 2FA** enabled and set the
   repository Actions secret `NPM_TOKEN`. A token limited to unrelated existing
   packages will not grant permission to create this package. Keep its value
   outside Git, documentation, artifacts and chat messages.
4. Confirm the release version in `package.json`, `package-lock.json` and
   `CHANGELOG.md`. The first published package version is `0.7.1`;
   it does not need to start at `0.1.0`.
5. Run the full checks and review the archive before creating a release tag.
6. Only when publication is intended, create and push the matching tag:

   ```bash
   git tag -a v0.7.1 -m "TourKit 0.7.1"
   git push origin v0.7.1
   ```

The tag push is the publication trigger. Do not use it as a build-only test.
An interactive npm login and publish with 2FA is another bootstrap route;
local publication does not provide the workflow's GitHub provenance context.

### Subsequent publications with Trusted Publishing

After the package exists, configure its npm Trusted Publisher with owner
`deecalov`, repository `tourkit` and workflow filename `release.yml`. Enable
direct `npm publish` in Allowed actions if that is the chosen release mode.
The existing job uses GitHub-hosted Ubuntu and has `id-token: write`.

Current npm documentation requires npm CLI >= 11.5.1 and Node.js >= 22.14.0
for OIDC. The release job uses Node.js 24 and upgrades npm. Verify OIDC
publication before removing the bootstrap secret; a successful `npm whoami`
is not a test of OIDC publication permissions. A newly configured publisher
must complete its first successful publish within npm's current two-day
validation window.

### Reviewed artifact and dry run

After `npm run prepublishOnly`, create the package in a directory outside this
repository and inspect its file list:

```bash
node -e "require('node:fs').mkdirSync('../tourkit-release', { recursive: true })"
npm pack --json --pack-destination ../tourkit-release
npm publish ../tourkit-release/sitetourkit-0.7.1.tgz --dry-run --ignore-scripts --access public
```

`--ignore-scripts` is appropriate here because the validation/build lifecycle
has already run. The tarball is the checked artifact; dry-run does not upload
it. A successful dry-run verifies packaging, not registry write permission,
2FA configuration or production provenance generation.

The current package allowlist includes `dist/` without source maps,
`package.json`, `README.md`, `LICENSE` and `CHANGELOG.md`. Review new files on
each release. A ZIP intended for file-copy consumers should use the same
checked payload, with all referenced declaration files and optional entries.

### Confirm registry availability

Successful `npm publish` output can precede public availability by several
minutes. During the first release, npm temporarily exposed only a
`0.0.0-stage` placeholder while processing the upload. Version `0.7.1`
became available automatically; no manual approval was required for this
direct-publish workflow. Do not retry publication or change the version solely
because the initial registry lookup returns 404.

Before announcing a release, confirm its exact version and intended dist-tag,
download its registry tarball, verify `dist.integrity` and `dist.shasum`, and
install it in a clean consumer project. Attach that verified tarball and a ZIP
of the same contents to GitHub Releases, along with `SHA256SUMS.txt`.

### Recommended workflow improvements

The existing release job publishes the directory and creates a release with
notes, but attaches no compiled assets. To provide downloadable builds:

1. Add a manual build-only entry that runs the checks and retains a candidate
   archive without publishing or creating a version tag.
2. Pack once, record the file manifest and SHA-256 sums, and test that archive.
3. Publish that exact `.tgz` to npm, then verify registry `dist.integrity`
   against the candidate.
4. Attach the same archive, the corresponding file-copy ZIP and checksums to
   the GitHub Release. Do not rebuild a different payload for a second channel.
5. Keep GitHub Releases usable independently if npm publication is postponed;
   the current job creates a GitHub Release only after npm succeeds.

These are preparation recommendations, not capabilities already implemented
by the existing workflow.

Official references: [npm public packages](https://docs.npmjs.com/creating-and-publishing-unscoped-public-packages/),
[npm 2FA requirements](https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification/),
[Trusted Publishing](https://docs.npmjs.com/trusted-publishers/),
[npm publish and dry-run](https://docs.npmjs.com/cli/v11/commands/npm-publish/),
and [custom GitHub Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Undoing a release

Keep the previous working Git revision and npm version available. A Pages
rollback rebuilds a known working revision through the Pages workflow. For an
npm regression, publish a new patch release after validation; moving an existing
Git tag does not replace the already published npm artifact.
